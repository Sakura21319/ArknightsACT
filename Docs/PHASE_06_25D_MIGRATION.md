# Phase 06 — 2.5D Migration

This document describes the 2.5D migration baseline that Phase 07 builds on.

## Current production direction

- True 3D XZ world and collisions.
- Fixed low-oblique orthographic camera.
- Existing 2D Spine characters rendered as camera-facing billboards.
- Player uses `CharacterController` and `PlayerMotor25D`.
- Enemies use 3D perception, line-of-sight occlusion and lightweight waypoint navigation.
- Combat, collectibles and roguelite systems remain dimension-agnostic where practical.

## Player locomotion contract

`IPlayerLocomotion` is shared by the old side-view motor and the 2.5D motor:

```csharp
public interface IPlayerLocomotion
{
    bool IsGrounded { get; }
    bool IsMoving { get; }
    int FacingSign { get; }
    Vector3 PlanarForward { get; }
    float PlanarSpeed { get; }
}
```

This keeps attack, dash, skills and presentation from depending directly on one physics backend.

## Ch'en presentation

The 2.5D player keeps the authored Ch'en animation mapping from the validated 2D implementation:

- Basic 1: first half of `Attack`.
- Basic 2: second half of `Attack`.
- Basic 3: `Skill`.
- Skill 1: `Skill_2` + `Skill_End_2`.
- Skill 2: `Skill_3` + `Skill_End_3`.

Movement uses the hidden Ch'en base-motion source and `SpineBoneMotionRetarget2D`; the visible combat skeleton remains under the camera-facing presentation billboard.

## 2.5D combat

- Basic attacks use oriented 3D overlap boxes plus a small close-range frontal safety volume.
- Skill 1 uses an oriented 3D volume and checks height/occlusion.
- Skill 2 searches in 3D and filters by height/occlusion.
- Dash drives the `CharacterController` directly while preserving the generic invulnerability source.
- Player attacks and skills do not intentionally hit through solid cover or floors.

`DamageContext.Knockback` is still `Vector2`, so 2.5D attacks currently avoid arbitrary XZ knockback.

## Enemy perception and navigation

The 2.5D enemy brain requires an initial front-facing view-cone acquisition plus world line of sight. Geometry can block acquisition. Once alerted, enemies remember the target for a limited period and can use `PrototypeNavigationGraph25D` to route around obstacles and across the two-floor ramp.

Enemy attacks re-check range, vertical difference and line of sight after the animation wind-up.

## Death presentation

2.5D enemies:

- hide the vision warning immediately on death,
- disable collision immediately,
- preserve the authored death animation briefly,
- then destroy the corpse object.

## Camera hierarchy

```text
CameraRig25D        <- CameraFollow25D
└── Main Camera     <- CameraShake2D
```

This keeps camera follow and shake from both writing to the same local transform.

## World-space feedback

`WorldHealthBar2D` and floating damage numbers face `Camera.main` in 2.5D. Treasure chests use smaller world-health-bar layout overrides.

## Generated prototype assets

`ArknightsACT > Build Prototype Scene` remains the production scene entry point.

Phase 06 used the fixed 2.5D arena generated by `Prototype25DSceneBuilder`. Starting in Phase 07, `PrototypeRun` reuses that builder only for validated camera/lighting/material setup, removes the fixed `[3D Map]`, and lets the exploration stage runtime materialize the random stage layout at Play time.

## Phase 07 handoff note

The old `PrototypeRoomLoopController` remains in the repository as a fallback/legacy room-mode implementation, but the current Phase 07 `PrototypeRun` generation path does **not** create or start it. The active flow is now:

```text
RogueliteStageMapController
    -> random 4 / 6 / 9 logical blocks
RogueliteStageRuntimeController
    -> physical chunk assembly
    -> block entry activation
    -> persistent enemies / treasure
    -> fixed Boss endpoint
    -> next-stage entrance
```

This keeps the Phase 06 combat/presentation work intact while allowing the run structure to move from isolated rooms to exploration regions.

## Validation

All repository-side changes are source/static changes only until validated in a local Unity Editor. Rebuild `PrototypeRun` after pulling changes that modify editor factories or generated scene composition.
